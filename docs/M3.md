# M3: serial coordinator and real training workers

Implemented 2026-10-11: a CPU coordinator, two independent stage workers, real forward/backward/FP32 AdamW execution, launch commands, process-level CPU verification, and final diagnostic snapshot comparison. Target Windows CUDA + Mac MPS acceptance remains pending. No checkpoint save/resume is implemented; an interrupted run must start from deterministic initialization with a fresh run ID. M4 supplies durable recovery next.

## Runtime ownership and execution

`coordinator.py` owns CPU batches, assignments and the serial schedule. Its parameter manifests use meta tensors with no parameter storage. `worker.py` creates only its assigned stage and AdamW state. `runtime.py` connects authenticated sessions to state gates and absolute phase deadlines; `train_cli.py` exposes runnable launches. All wire messages and port **29550** remain as specified in [PROTOCOL](PROTOCOL.md).

For each microbatch, the suffix validates and retains targets before the coordinator releases input to the prefix. The prefix retains its activation graph and sends detached CPU bytes. The suffix copies the authenticated activation onto its device, detaches it and sets `requires_grad_(True)`, computes summed cross-entropy divided by the **whole step's** valid-token count, then backpropagates and returns that leaf's gradient. The prefix calls backward on its retained output using the received gradient, without another division. Saved graphs are released before completion replies. K=1..4 serial accumulation is supported; at most one microbatch is in flight.

Both workers must pass gradient checks before either update. The worker gate marks APPLYING before calling the real optimizer; synchronized parameter/moment checks precede STEP_APPLIED. Both APPLIED replies precede commits, and both COMMITTED replies precede the next step. Malformed tensors, missing gradients, nonfinite state, exceptions, interrupts and disconnects close the run without update retries. The CLI emits no periodic heartbeats while synchronous device work runs; the declared compute deadline applies. A Python deadline cannot forcibly interrupt a hung device kernel: the peer stops on timeout and the operator may need to terminate the affected worker process.

Normal runs hold one step's CPU batches (K≤4), one stage graph, bounded communication buffers, and scalar counters. Step reports stream to JSONL. Full-weight diagnostic snapshots are explicitly restricted to the 875,264-parameter fixture (b≤2, T≤32, K≤4), stay on the worker's local disk, and retain only the latest step. They add substantial I/O and memory overhead and must not be used as a throughput benchmark or checkpoint. `local_run.py` and `snapshot_check.py` are separate tiny-model validators that intentionally assemble reference/snapshot tensors; the training coordinator never does.

## Run local process verification

**Mac/Linux, zsh; project root; environment from SETUP:**

```zsh
PYTHONPATH=src .venv/bin/python -m hive_train.local_run --steps 10 --output artifacts/validation/m3-single.json
PYTHONPATH=src .venv/bin/python -m hive_train.local_run --steps 10 --microbatches 2 --scenario masked --output artifacts/validation/m3-masked.json
PYTHONPATH=src .venv/bin/python -m hive_train.local_run --steps 100 --scenario pattern --output artifacts/validation/m3-pattern.json
```

Expected: each command exits 0 with `status: pass`. Two child Python processes execute real worker training using authenticated inherited socketpairs; the parent performs coordination and tiny CPU reference verification. Every step compares logits, loss, boundary gradients, all parameter gradients/updates and Adam moments/counters under CPU tolerances. Pattern mode evaluates a fixed sequence start (157) reserved from training, at step 0/every 10/final; individual byte transitions naturally overlap within this synthetic repeating pattern. Initial distributed evaluation uses the actual workers' pre-update parameters. The 100-step check requires improved loss and reference agreement. This is synthetic correctness/learning evidence, not language-quality evidence.

The inherited-descriptor launcher requires POSIX; Windows uses TCP commands below, with `--allow-cpu` on the coordinator and `--device cpu` on both workers for CPU emulation. The local verifier uses a private temporary directory for its secret and diagnostic tensors, removes that directory on completion, and keeps only the requested JSON report. Failure exits nonzero and includes bounded worker logs. Missing torch means use the selected environment; unavailable socket inheritance means use the TCP launches where permitted. No project installation is required when `PYTHONPATH=src` is set.

## Run on Windows CUDA and Mac MPS

First complete [SETUP](SETUP.md), [M1 device equivalence](M1.md) and [M2 authenticated link checks](M2.md). Use identical source copies and matching PyTorch base releases. Obtain a new 32-byte private run key using M2's `keygen` instructions, name it `.secrets/m3.key`, and transfer the same file privately to the other machine. Keep the existing scoped firewall rule for the Windows Python executable, local interface and Mac peer. Stop earlier diagnostic listeners before reusing port 29550.

The following commands exist but are **unverified on the target hardware/Windows shell**. All terminals use the project root as working directory and the `.venv` from SETUP. Prepare all three terminals first; start both workers within 30 seconds after the coordinator begins listening.

**A, PowerShell terminal 1 — coordinator:**

```powershell
Set-Location "$env:USERPROFILE\Documents\hive-train"
$env:PYTHONPATH = "src"
.\.venv\Scripts\python.exe -m hive_train.train_cli coordinator --bind 0.0.0.0 --secret-file .secrets\m3.key --steps 10 --output artifacts\training\m3-coordinator.json
```

Expected: `Listening on 0.0.0.0:29550`, then waits for both authenticated workers. It requires CUDA worker-0 and MPS worker-1 by default. `--allow-cpu` explicitly permits diagnostic CPU placement.

**A, ordinary PowerShell terminal 2 — CUDA prefix:**

```powershell
Set-Location "$env:USERPROFILE\Documents\hive-train"
$env:PYTHONPATH = "src"
.\.venv\Scripts\python.exe -m hive_train.train_cli worker --host 127.0.0.1 --worker-id worker-0 --device cuda --secret-file .secrets\m3.key --diagnostic-directory artifacts\training\m3-stage0 --output artifacts\training\m3-cuda.json
```

**B, Terminal/zsh — MPS suffix:**

```zsh
cd "$HOME/Documents/hive-train"
read 'HIVE_HOST?Windows local IPv4: '
PYTORCH_ENABLE_MPS_FALLBACK=0 PYTHONPATH=src .venv/bin/python -m hive_train.train_cli worker --host "$HIVE_HOST" --worker-id worker-1 --device mps --secret-file .secrets/m3.key --diagnostic-directory artifacts/training/m3-stage1 --output artifacts/training/m3-mps.json
```

Expected: all three commands finish with exit 0 and `status: pass`; workers report 10 committed steps and parameter version 10. The coordinator writes `m3-coordinator.steps.jsonl` with per-step loss, valid tokens, version, batch-plan hash and elapsed time. Reports record environments and capabilities; local device checks require a real backward/update and reject unavailability or enabled MPS fallback. These pass results demonstrate execution but do not by themselves establish numerical equivalence—compare snapshots next.

Snapshot directories must be new. For another attempt use new output paths/directories and a fresh key; never overwrite evidence from a run you still need. For K=2 masking, add `--microbatches 2 --scenario masked` to the coordinator only. `empty_microbatch` checks an ignored microbatch within a nonempty step; `pattern` supplies learnable byte patterns. Normal runs may omit `--diagnostic-directory` after correctness checks; no model is saved on STOP in that mode.

Connection refused/timeout: check listening process, correct local IP, scoped firewall and client isolation as in SETUP. Peer EOF can mean the other worker failed: inspect **all three** reports. Admission timeout requires a fresh attempt with all terminals ready. `FileExistsError` for snapshots requires a new diagnostic directory. Device unavailable/unsupported operation: retain its traceback/report and diagnose locally; do not enable silent fallback. Any failure after update may leave different live versions; all processes stop, and M3 cannot resume that partial run.

## Compare target results to the CPU reference

After a successful ten-step diagnostic run, privately collect the coordinator JSON and both complete snapshot directories on one machine. They contain model/gradient data; the filenames below assume all three are under local `artifacts/training/`. Use the same PyTorch base release as the workers. The checker requires matching run/config/stage identifiers, replays the deterministic CPU reference, and compares the **final step** including update deltas and Adam counters. It is not a checkpoint loader, and only the standard tiny fixture is accepted.

**B, zsh; project root** (or A's venv executable with equivalent paths in PowerShell):

```zsh
PYTHONPATH=src .venv/bin/python -m hive_train.snapshot_check --coordinator-report artifacts/training/m3-coordinator.json --stage0 artifacts/training/m3-stage0 --stage1 artifacts/training/m3-stage1 --output artifacts/validation/m3-target-comparison.json
```

Expected: `status: pass`, `tier: cross_device` in the report, and finite error metrics under [VALIDATION](VALIDATION.md) thresholds. A wrong run ID, missing/corrupt file, mismatched torch release, absent gradient/update or numerical mismatch fails. A pass covers the final captured step; the local process verifier covers every step on CPU. Repeat target one-step/ten-step/K=2 scenarios and collect short-learning curves before marking M3 target acceptance complete. A local text corpus, sustained target memory/performance measurements and target held-out-quality validation remain pending.

## Evidence and next gate

Tested in the supplemental macOS 15.5 ARM64 Python 3.11.15/PyTorch 2.13.0 CPU environment, rather than the selected deployment pair: **122 tests pass**; all three legal block cuts for ten threaded-worker steps each; separate worker processes for ten K=1 steps, ten masked K=2 steps and 100 pattern steps; reference comparisons, malformed targets/activations, missing gradients, interruptions and disconnects after real updates. The 100-step process test's reserved-start pattern validation loss fell from **5.587015 to 4.377883**, matching its CPU reference. Reports are under `artifacts/validation/m3-*.json`.

Independent review checked autograd, normalization, state ownership, deadlines and failure handling. Integration fixes included converting PyTorch's version object to a plain wire string, consistent worker success status, and per-peer heartbeat versions. Tests use numerical tolerances even where observed CPU differences are zero. All CPU comparisons use one intra-op thread; changing thread counts can change near-zero gradients and Adam updates and requires its own recorded baseline.

The sandbox still denies IPv4 loopback bind, verified 2026-10-11. No actual TCP routing, Wi-Fi, CUDA/MPS training, capacity gain, sustained memory limit or speedup has been established. Next: collect target reports using these commands; then M4 implements bounded stage-local checkpoint save/restore and coordinated restart, with fault injection and resumed-reference comparison.
