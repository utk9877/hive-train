# Research and component assessment

Research cut-off and access date for **every linked source below: 2026-10-07 (Asia/Kolkata)**. Sources are original papers, authors' repositories, and official documentation. Mutable repository branches and `stable` documentation are discovery evidence, not dependency locks; record exact versions/commits when adopting a component. The package baseline is authoritative in [SETUP.md](SETUP.md).

## Evidence and conclusion

- **Documented (D):** explicitly described by official documentation or source repository; not necessarily demonstrated on our machines.
- **Author-reported (A):** experimental result or capability reported by the authors; not independently reproduced here.
- **Engineering inference (I):** our judgment derived from these sources, to be validated.
- **Unverified (U):** not established by this review. “Code not located” does not mean code cannot exist.
- **Personally tested (T):** none of the external systems or target accelerator configurations in this document. Reading source material is not a hardware test.

**I — Recommendation:** reuse PyTorch's local tensor operations and autograd; implement a narrow, synchronous two-stage runtime with explicit boundary gradients and bounded CPU-buffered TCP. This solves the mixed native Windows/macOS integration problem without requiring mixed-device collectives. It does not establish a new training algorithm or a speed advantage. See [ARCHITECTURE.md](ARCHITECTURE.md), [PROTOCOL.md](PROTOCOL.md), and the decision record in [DECISIONS.md](DECISIONS.md).

## Platform foundation

**D — PyTorch distributed:** the official backend documentation calls Windows support prototype and explicitly excludes NCCL on Windows. macOS build availability must also be checked; the distributed documentation distinguishes OS support from how binaries are built. Its backend/device matrix is not a promise of MPS collectives. **I:** CPU Gloo could be investigated later where both builds expose it, but it provides no advantage necessary to the first two-worker transport. Avoid making `torch.distributed`, NCCL, or a custom collective a prerequisite. [Official distributed backend documentation](https://docs.pytorch.org/docs/stable/distributed).

**D — PyTorch pipeline parallelism:** the documented runtime splits models, schedules microbatches, propagates gradients, and supports GPipe/1F1B variants across hosts. `PipelineStage` manages communication and intermediate buffers; shapes/dtypes must match the stage contract. The current page labels the API alpha. **U:** these features do not demonstrate native Windows CUDA plus macOS MPS in one pipeline. **I:** local autograd is low integration effort; adapting this distributed runtime and its process-group communication is materially higher effort than our restricted serial protocol. Public source is available under PyTorch's [BSD-style license and included component notices](https://github.com/pytorch/pytorch/blob/main/LICENSE). [Official pipeline documentation](https://docs.pytorch.org/docs/2.14/distributed.pipelining.html).

**D/A — GPipe:** full-parameter training of layer sequences with microbatch pipelines is established prior art. The paper reports large-model training on accelerators; its scaling results are not Wi-Fi measurements. **I:** reuse synchronous update semantics and schedule reasoning when multiple microbatches are introduced, not the reported speedups. Google's original public implementation is described in its [GPipe release article](https://research.google/blog/introducing-gpipe-an-open-source-library-for-efficiently-training-large-scale-neural-network-models/); we are not incorporating that implementation, and its per-file license has not been audited here. [Original paper](https://arxiv.org/abs/1811.06965).

## Low-bandwidth and decentralized training

### SWARM

**D/A:** SWARM performs model-parallel training over unreliable heterogeneous workers using changing pipelines, balancing, and compression. The paper reports training a Transformer with about 1B shared parameters (about 13B before sharing) on preemptible T4 GPUs below 200 Mb/s. This is full training, not an adapter demo, but parameter sharing/compression and its multi-worker setting matter when interpreting capacity and speed. [Paper](https://proceedings.mlr.press/v202/ryabinin23a.html), [paper PDF](https://proceedings.mlr.press/v202/ryabinin23a/ryabinin23a.pdf).

**D:** the [official repository](https://github.com/yandex-research/swarm) contains a prototype and experiment material, and explicitly says some paper features, including stage rebalancing, are not included. **I:** reuse partitioning, communication, and experimental ideas; direct adoption is high effort and does not establish mixed CUDA–MPS support. **U:** no clear root code license was located in the inspected repository listing; audit each desired file and obtain permission as needed before copying. A public repository alone is not a reusable-code license. Missing rebalancing in this repository does not make our rebalancing idea novel.

### Hivemind

**D:** [Hivemind](https://github.com/learning-at-home/hivemind) provides a DHT, decentralized parameter averaging, and remote trainable mixture-of-experts/backpropagation facilities. Its model-averaging path generally replicates the model; its distributed-expert path has different ownership/routing semantics from our fixed dense transformer. Full-parameter training is supported in relevant workflows, but not every usage pools model capacity. Networks are decentralized and may have slow/unreliable peers. The project develops primarily on Linux, lists partial macOS support, and lists experimental Windows use through WSL. **I:** libp2p discovery, compression, and averaging become relevant with many replicas; they add setup and lifecycle complexity for two fixed native workers. **U:** no supported mixed native Windows CUDA–MPS run was verified. Public code is [MIT licensed](https://raw.githubusercontent.com/learning-at-home/hivemind/master/LICENSE); preserve its notices and audit dependencies if reused.

### DiLoCo, OpenDiLoCo, and newer variants

**D/A:** [DiLoCo](https://arxiv.org/abs/2311.08105) trains full model replicas on compute islands with many local optimizer steps between synchronization rounds. Authors report drastically reduced communication while retaining competitive model quality. An island may itself use model parallelism; the algorithm alone does not make one replica fit across two undersized machines. **I:** using our two devices as different DiLoCo replicas would miss the capacity objective; it becomes relevant once there are multiple complete distributed replicas.

**D:** [OpenDiLoCo](https://github.com/PrimeIntellect-ai/OpenDiLoCo) exposes a training implementation using FSDP and Hivemind and reusable optimizer components. Its installation/examples target CUDA-style multi-GPU training, not our native mixed-device pair. The README now states it is unmaintained and points to Prime. Public code is [Apache-2.0](https://github.com/PrimeIntellect-ai/OpenDiloco/blob/main/LICENSE). **I:** high integration effort, altered optimizer semantics, and replica memory requirements make it unsuitable for milestone one. Reuse its evaluation practices or outer-optimizer concepts later. [Replication paper](https://arxiv.org/abs/2407.07852).

**A:** [Decoupled DiLoCo, 2026](https://arxiv.org/abs/2604.21428) extends island training toward resilience and asynchronous progress. **I:** this constrains claims about novel adaptation/failure tolerance; it does not remove the need to fit each island's replica. **U:** a reusable implementation/license and the target mixed-device combination were not established in this review. Do not adopt algorithmic changes without new convergence baselines.

### FusionLLM and heterogeneous compressed pipelines

**A:** [FusionLLM](https://arxiv.org/abs/2410.12707) reports full training with remote differentiation over an operator DAG, heterogeneous software/devices, a workload estimator/partition scheduler, and adaptive compression of activations and gradients. Experiments train GPT-2 and ResNet-101 on 48 GPUs with links spanning 8 Mb/s–10 Gb/s. **I:** this directly precedes proposed claims about low-bandwidth heterogeneous remote backward, automatic assignment, and adaptive compression. Ideas and evaluation settings are reusable; replacing our two-stage model with a general DAG executor would be high effort. **U:** public author code/license and mixed CUDA–MPS support were not located/verified; no source is incorporated.

**A:** [Heterogeneous Low-Bandwidth Pre-Training of LLMs, 2026](https://arxiv.org/abs/2601.02360) combines SparseLoCo with compressed pipeline replicas and studies 178M–1B parameter language models. Some participants host full replicas; weaker groups jointly host a replica, with subspace compression for boundary activations and gradients. **I:** this is prior art for mixing capacity pooling and low-communication replica training. Compression changes training numerics, so it belongs after exact FP32 correctness and matched-quality evaluation. **U:** exact native OS/device support, reusable public implementation, and code license were not established; the [paper's CC BY 4.0 notice](https://arxiv.org/html/2601.02360v1) licenses the paper, not unidentified code.

## Heterogeneous placement and adaptation

### HetPipe and AMP

**A:** [HetPipe](https://www.usenix.org/conference/atc20/presentation/park) combines pipelined model parallelism with data parallelism so GPUs unable to hold a complete training model can contribute. It uses profiled layer costs and memory-constrained partitioning. Its evaluation uses heterogeneous NVIDIA GPUs on Ubuntu, modified TensorFlow, and 56 Gb/s InfiniBand; slow heterogeneous networking was not its evaluated target. It includes bounded-staleness training semantics, unlike our synchronous baseline. **I:** profiling/placement ideas are valuable; the runtime is not a drop-in and reported throughput does not transfer to Wi-Fi. **U:** a usable author code release/license was not established. [Original implementation and experiment details](https://www.usenix.org/system/files/atc20-park.pdf).

**D/A:** [AMP paper](https://arxiv.org/abs/2210.07297) and [official code](https://github.com/DachengLi1/AMP) describe full-training strategy search using a cost model and dynamic programming for heterogeneous models/GPU clusters. The implementation includes a DeepSpeed fork and cluster-oriented execution. **I:** its representation, memory constraints, and measured cost approach are useful; the two-worker case needs only split enumeration, not a port of the optimizer/search stack. No MPS/Windows interoperability is demonstrated. **U:** no clear top-level license was found in the inspected listing; its embedded third-party code needs a separate license audit. Direct integration is high effort.

### HetAuto, Tessera, CrossPipe, and runtime adaptation

**A/D:** [HetAuto, EuroSys 2026](https://i.cs.hku.hk/~cwu/papers/gcqi-eurosys26.pdf) studies full training across clusters including NVIDIA GPUs and Ascend NPUs. It combines strategy search, cost estimation, communication-aware scheduling, resharding, and hardware abstraction on Megatron-LM. Although the paper says code is available, the linked [public repository](https://github.com/Guicheng-Qi/HetAuto) currently contains a README saying release awaits internal review. Treat implementation availability as unverified, not a ready dependency. **I:** strong precedent for cross-vendor full training and heterogeneous automatic parallelism; high porting cost and no established Windows/MPS path. Reuse conceptual constraints and comparisons. **U:** a code license is not available from that placeholder; verify before incorporation.

**A:** [Tessera, OSDI 2026](https://www.usenix.org/conference/osdi26/presentation/hu-weifang) addresses heterogeneous **model layers**, especially MoE/attention combinations, using overlap-aware partitions and dynamic bubble filling. It reports production full pretraining on thousands of GPUs. Do not conflate layer heterogeneity with proof of CUDA–MPS interoperability. **I:** a partition model should predict the actual schedule, not blindly sum isolated kernel times; runtime scheduling adaptation already exists. **U:** reusable public code/license was not identified from the primary page. Incorporating its MoE machinery is outside scope.

**D/A:** [CrossPipe](https://www.usenix.org/conference/atc25/presentation/chen-tiancheng) models both bandwidth and latency and optimizes full-training pipeline schedules under memory constraints across datacenters. Its [paper](https://www.usenix.org/system/files/atc25-chen-tiancheng.pdf) links a [public Megatron-based implementation](https://github.com/spcl/crosspipe), whose reproduction environment uses an NVIDIA container and modified PyTorch for delay injection. **I:** reuse its communication-aware scheduling framework as prior art; evaluate any borrowed cost model against Wi-Fi variability. Direct porting is high effort. The [license file](https://github.com/spcl/crosspipe/blob/main/LICENSE) supplies BSD-style default terms plus third-party notices, including Apache-2.0; inspect each copied file. **U:** our backend pair is not established.

**A/D:** [PipeTransformer](https://arxiv.org/abs/2102.03161) dynamically freezes converged layers, packs active trainable layers, and expands data-parallel replicas; [public code](https://github.com/Distributed-AI/PipeTransformer) exists. It is training with changing trainable subsets, not our all-parameters-active objective. [Oobleck](https://arxiv.org/abs/2309.08125) provides resilient full training using pipeline templates and replicas. **I:** both are precedents for dynamic assignment/reconfiguration, but their cluster/replica or freezing assumptions differ. Reuse concepts; do not implement redundant replicas that erase our capacity gain. **U:** usable versions/licenses for direct incorporation were not audited (PipeTransformer's inspected root lists no license); the Oobleck paper, not a similarly named audio repository, is the relevant work.

**A:** [PIPEMORPH, NSDI 2026](https://www.usenix.org/conference/nsdi26/presentation/wu-tianyuan) adapts pipeline schedules under communication stragglers and stages communication through host memory/CPU-side RDMA. It reports full-training iteration improvements in a cluster setting. **I:** adaptive scheduling and host staging already have explicit prior art; RDMA dependencies do not fit this project. Reuse its distinction between schedule stalls and transport stalls. **U:** public implementation/license and native MPS support were not established in this review.

## Cross-vendor alternatives and inference traps

**A:** [Joint Training on AMD and NVIDIA GPUs, 2026](https://arxiv.org/abs/2602.18007) reports full training using CPU-forwarded communication and a more advanced direct-device path on multi-vendor clusters. [HetCCL, January 2026](https://arxiv.org/abs/2601.22585) unifies NCCL/RCCL with RDMA. These are concrete cross-vendor training precedents; neither establishes Apple MPS or native Windows support. **I:** CPU staging is a sensible interoperability boundary, not a novel invention. Reuse the design rationale; adopting vendor collectives/RDMA is high effort and unnecessary. **U:** reusable author source/license and compatibility with our machines were not established. “HetCCL” also names a [separate May 2026 paper](https://arxiv.org/abs/2605.31000); keep authors and identifiers distinct.

**D/A — Petals:** [public repository](https://github.com/bigscience-workshop/petals), [original paper](https://aclanthology.org/2023.acl-demo.54.pdf), [follow-up paper](https://arxiv.org/abs/2312.08361). It hosts model blocks across Internet-connected peers for inference and parameter-efficient fine-tuning/custom trainable extensions. Backward through hosted blocks is not evidence that every hosted base-model parameter is updated. **I:** remote activation/gradient handling and private-swarm concepts are useful; making its serving system our full pretraining runtime would require substantial redesign. **U:** full-base-model training of our mixed device pair is not demonstrated. Public code is [MIT](https://github.com/bigscience-workshop/petals/blob/main/LICENSE); model weight licenses are separate.

**D — HexGen:** [paper](https://arxiv.org/abs/2311.11514), [repository](https://github.com/Relaxed-System-Lab/HexGen). Its asymmetric tensor/pipeline partitions and heterogeneous network scheduling are for generative inference. The setup specifies CUDA; it is not a CUDA–MPS full-training system. **I:** useful placement inspiration, high runtime integration cost, no backward/optimizer proof. Public code is Apache-2.0 per the repository license declaration; verify vendored components if used. Newer [HexGen-3](https://github.com/Relaxed-System-Lab/HexGen-3) also addresses serving and requires GPU/RDMA infrastructure; it does not change this conclusion.

**D/A — DRIFT:** the [repository](https://github.com/TaewoooPark/DRIFT) specifically describes Windows/Linux CUDA plus Mac MPS pipeline **inference** using a framework-neutral TCP byte protocol. Authors publish inference parity claims. **I:** this is directly relevant transport/platform precedent, but token agreement is not gradient/update equivalence; do not transfer its broad bitwise language into our acceptance criteria. Reuse ideas only after inspecting tests and security design; training lifecycle integration remains substantial. It is publicly [MIT licensed](https://github.com/TaewoooPark/DRIFT/blob/main/LICENSE). **U:** no full training or personal reproduction is established here.

## DeepSpeed and MLX

**D — DeepSpeed:** [accelerator abstraction](https://www.deepspeed.ai/tutorials/accelerator-abstraction-interface/) separates vendor backends; the [setup guide](https://www.deepspeed.ai/tutorials/accelerator-setup-guide/) updated October 5, 2026 now explicitly documents Apple MPS **single-device training**, ZeRO/offload support, and CPU-staged Gloo. It explicitly calls multi-machine Gloo training untested and notes no native MPS collective backend. Its verified Mac example is M5 Max/macOS 26, not our M4 Air. Thus “DeepSpeed cannot train on MPS” is outdated; “DeepSpeed supports our mixed pair” is unsupported. **I:** investigate later as a single-machine offload comparator, with separately verified installation and optimizer semantics. Shared Mac DRAM does not grow through CPU offload. Mixed-runtime adoption is high risk for the first milestone. Public [DeepSpeed source](https://github.com/deepspeedai/DeepSpeed) is [Apache-2.0](https://github.com/deepspeedai/DeepSpeed/blob/master/LICENSE).

**D — MLX:** [current distributed documentation](https://github.com/ml-explore/mlx/blob/main/docs/src/usage/distributed.rst) lists TCP ring, MPI, JACCL (RDMA over Thunderbolt), and NCCL for CUDA environments. Therefore it is inaccurate to assume today's MLX is categorically Apple-only. [MLX](https://github.com/ml-explore/mlx) supplies autograd and operations suitable for training; distributed primitives are not automatically a capacity-sharded training application. **I:** useful future backend or Mac-only comparator; a second tensor/autograd framework expands numerical, checkpoint, and platform work. JACCL requires hardware absent here. **U:** a supported native Windows CUDA–macOS MLX training pipeline is not demonstrated by this backend list. Code is [MIT](https://github.com/ml-explore/mlx/blob/main/LICENSE).

**I — CUDA translation:** no concrete first-version operation requires CUDA-to-Metal translation because the model uses ordinary native PyTorch operations. Do not add a translator. As an adjacent example, [ZLUDA](https://github.com/vosen/ZLUDA) is a CUDA compatibility project with public Apache/MIT license files; that description does not establish MPS support, distributed autograd, or our training application. A translator would add compatibility work without solving tensor ownership, gradient exchange, or recovery. Reconsider only if a later indispensable kernel cannot be expressed natively; audit that specific translator/backend/license then.

## Novelty assessment and research hypotheses

The following are established ideas, not project novelty: pipeline capacity pooling (GPipe, HetPipe); heterogeneous partition search (AMP, HetAuto); low-bandwidth training/remote backward (SWARM, FusionLLM); hybrid compressed replicas (2026 low-bandwidth pretraining); runtime scheduling/reconfiguration (PipeTransformer, Oobleck, PIPEMORPH, Tessera); CPU-mediated mixed-vendor transport (2026 AMD/NVIDIA work and DRIFT inference).

Our potential contribution is an experimentally supported **combination and evaluation**, not a claim of being first. Search coverage is broad but not an exhaustive systematic review; a publication claim needs a focused follow-up on split learning, migration-cost-aware placement, online scheduling, and cross-vendor training.

| Hypothesis | Necessary comparison | Evidence that would weaken it |
|---|---|---|
| A small native CUDA–MPS runtime makes full-parameter capacity pooling practical on student hardware | Both accelerator-only baselines; practical CPU/offload baselines; bounded RAM and checkpoint measurements | Capacity exists only by changing precision, optimizer, objective, or silently falling back |
| Measured static enumeration predicts useful splits under Wi-Fi constraints | Equal-layer split, best observed static split, held-out network traces | Prediction error outweighs the improvement or only a cherry-picked trace benefits |
| Conservative adaptation wins after sustained compute/network shifts | Frozen best initial split; best hindsight static split; aggressive-reacting baseline | Migration consumes the saved time, oscillates, or loses training equivalence |
| A compact public trace/benchmark suite reveals cross-platform pitfalls | Repeatable loss/gradient/update, memory, network, and recovery artifacts | Findings cannot be reproduced on another configuration |

For the third hypothesis, only migrate at a drained safe boundary when a conservative estimate satisfies `remaining_steps × lower_bound(current_step_time − candidate_step_time) > upper_bound(migration_time) + safety_margin`. Migration includes draining, parameters **and optimizer state**, host staging/network, deallocation/reallocation, checkpoint/manifest work, and warmup/resume; include uncertainty and a minimum residency/cooldown. This rule is **I**, a candidate engineering policy, not proven novelty. First evaluate it through trace replay and then real migrations. ## Incorporation policy

No external source code is incorporated by this planning run. Reusing an algorithmic idea with attribution differs from copying implementation. For any later code reuse, record upstream commit, exact files, their licenses and dependency notices. MIT/BSD components require retained notices; Apache-2.0 components require the applicable license/notice/change obligations. Unknown licenses block copying those files, not implementing independently described ideas. Model/dataset terms require their own review. This is a practical project bookkeeping rule; use the linked license texts as authority.
